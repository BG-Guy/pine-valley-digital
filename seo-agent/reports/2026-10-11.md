## Changes in this PR

All three changes are technical/structural, not copy changes, since there's no query data yet to drive copy decisions.

1. **Homepage (`/`)** — `index.html`
   - Added `<link rel="canonical" href="https://pinevalleydigital.com/" />`. No canonical tag existed before.
   - Added `Organization` JSON-LD (`name`, `url`, `email`) built only from facts already in the repo (the site name and the `hello@pinevalleydigital.com` address used in the contact section). No JSON-LD existed before.

2. **Lab page (`/lab.html`)** — `lab.html`
   - Added `<link rel="canonical" href="https://pinevalleydigital.com/lab.html" />`. No canonical tag existed before.

3. **All 14 service pages (`/services/*.html`)** — `src/pages/services/main.ts`
   - These 14 pages share one entry script (`src/pages/services/main.ts`), which already reads each page's `pvd-service` meta tag to look up its content. Added one block there that injects a self-referencing canonical link using that same slug, so every service page gets a canonical tag from a single source-of-truth edit instead of 14 near-duplicate HTML edits (per the playbook's guidance to touch a template when a fix applies to many pages).
   - Trade-off worth knowing: this canonical tag is added by JavaScript after the page loads, not present in the raw HTML Google first fetches. Google does render JS before using canonical tags, so this works, but a tag baked into each static HTML file is marginally more robust. If you'd rather have it static, say so and I'll add it to all 14 files directly (that would use most of a future week's page budget).

None of these touch a URL, title, or any visible copy — they're invisible-to-visitors technical fixes, low risk, and reversible via the `before.notes` in `seo-agent/changelog.jsonl`.

## Needs your decision

- **No `sitemap.xml`, no `robots.txt`.** Neither file exists anywhere in `public/` or the repo. This is almost certainly why Search Console's sitemap list came back empty. I did not create either file this run because:
  - `robots.txt` changes are explicitly proposal-only in this agent's guardrails.
  - A sitemap needs to enumerate all 16 pages (home, lab, 14 services) and would most naturally be generated at build time — similar to how `vite.config.ts` already scans `services/` for build entries — which is a build-config change outside `content_sources` (`index.html`, `services/`, `lab.html`, `src/sections/`), not a content edit.
  - **Recommended fix:** add a small build step or Vite plugin that writes `public/sitemap.xml` (or emits it into `dist/`) by reusing the same `readdirSync('services')` scan in `vite.config.ts`, then reference it from a new `robots.txt`. Happy to implement this next run if you'd like it in scope, or you can hand it to whoever owns build config.
- **Service-page canonical tags are JS-injected, not static** (see item 3 above) — confirm whether that's acceptable or you want them baked into each HTML file instead.
- **Thin homepage meta description.** "Pine Valley Digital — we build fast, modern websites." is 55 characters — well under the ~140-160 character range this playbook recommends for descriptions. I left it alone this run because without query data there's no evidence-based rewrite to make yet (rewriting without data risks guessing wrong). Worth a look once Search Console has data, or sooner if you want a stronger standing description.
